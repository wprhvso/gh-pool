# pool-runners

Self-hosted раннеры GitHub Actions поверх [pool](https://github.com/wprhvso/pool).
Контроллер держит в целевой репе эфемерный runner scale set, слушает её очередь
job'ов и на каждый job отправляет в пул задачу, которая разворачивает раннера
прямо внутри уже живого воркера.

```
job в очереди GitHub ──> контроллер ──POST /v1/tasks──> pool ──> воркер
        ▲                    │                                     │
        └────── раннер ◀─────┴─────── scale set + JIT-конфиг ───────┘
```

Пул — это двадцать джоб `ubuntu-latest`, которые и так поллят очередь. Раннер
там появляется за секунды: не нужно ни диспатчить воркфлоу, ни ждать, пока
GitHub выделит машину, ни платить за это REST-лимитом.

## Принципы

- Раннер — это задача пула, а не воркфлоу. Всё, что умеет пул — отмена, логи,
  статусы, — работает и с раннерами.
- Раннер эфемерный: одна job и до свидания. Ретраев нет, GitHub сам переставит
  job'у в очередь.
- Контроллер верит только статистике scale set: сколько job'ов назначено —
  столько раннеров и должно быть.
- REST-лимит GitHub тратится только на registration token, раз в час на репу.
  Очередь, JIT-конфиги и статистика живут на pipeline API, у которого лимита нет,
  а версия раннера берётся редиректом с `releases/latest` вообще без токена.
- Остановка не рвёт чужую работу: `Ctrl+C` снимает простаивающих раннеров и
  сносит scale set, а тех, кто в середине job'ы, оставляет доработать.

## Чем это отличается от nested-runner

| | nested-runner | pool-runners |
|---|---|---|
| откуда берётся раннер | `workflow_dispatch` своей репы | задача в пуле |
| задержка старта | десятки секунд плюс очередь Actions | RTT до сервера пула |
| REST-лимит на раннера | диспатч + опрос запусков | ноль |
| JIT-конфиг | age-шифрование, потому что input публичный | едет по токену пула |
| своя репа под раннеров | нужна | не нужна |
| уборка | отмена запусков | отмена задач |

## Что нажать

### 1. Токен на целевую репу

Fine-grained PAT с правом **Administration: read and write** на целевую репу —
из него делается registration token и им же удаляются раннеры. Классический
`repo` тоже подойдёт.

### 2. Конфиг

```bash
cp runners.toml.example runners.toml
```

```toml
jobs = 20
idle = "5m"
lifetime = "1h"

[pool]
server = "https://pool.example.com"
token = "клиентский токен пула"

[repos]
"alice/app" = "github_pat_..."
"alice/heavy" = { token = "github_pat_...", jobs = 40, label = "pool-big" }
```

### 3. Запуск

```bash
uv run pool-runners -c runners.toml --check    # проверить доступы и пул
uv run pool-runners -c runners.toml
```

Одна репа и без конфига — тоже можно:

```bash
GH_TOKEN=... POOL_SERVER=... POOL_CLIENT_TOKEN=... uv run pool-runners alice/app
```

### 4. `runs-on` в целевой репе

```yml
jobs:
  build:
    runs-on: pool
```

Метка — это имя scale set, то есть `label` из конфига. Массивы в `runs-on`
не работают.

## Конфиг

Ключи верхнего уровня — значения по умолчанию для всех реп, в таблице репы
их можно переопределить.

| ключ | по умолчанию | что задаёт |
|---|---|---|
| `token` | — | токен с правами админа на репу |
| `label` | `pool` | имя scale set, оно же метка для `runs-on` |
| `jobs` | `20` | потолок одновременных раннеров на репу |
| `idle` | `5m` | сколько раннер ждёт свою job, прежде чем вернуть слот пулу |
| `lifetime` | `1h` | сколько живёт раннер вместе с job'ой |
| `drain` | `1m` | сколько ждать доработки job'ов при остановке |
| `work` | `_work` | рабочая папка раннера, относительно его корня |
| `version` | последняя | версия `actions/runner`, если хочется пин |
| `sha256` | — | проверять архив раннера по хэшу (с `version`) |
| `[pool] server` | `POOL_SERVER` | адрес сервера пула |
| `[pool] token` | `POOL_CLIENT_TOKEN` | клиентский токен пула |

Без конфига то же самое читается из окружения: `GH_TOKEN`, `POOL_SERVER`,
`POOL_CLIENT_TOKEN`, `RUNNERS_LABEL`, `RUNNERS_JOBS`, `RUNNERS_IDLE`,
`RUNNERS_LIFETIME`, `RUNNERS_DRAIN`, `RUNNERS_WORK`, `RUNNERS_VERSION`,
`RUNNERS_SHA256`, `RUNNERS_DEBUG`.

## Как это работает

1. Контроллер заводит в целевой репе scale set с именем `label` и открывает
   message session.
2. Приходит `JobAvailable` — контроллер забирает job (`acquirejobs`) и смотрит
   в `totalAssignedJobs`: столько раннеров и нужно.
3. На каждого недостающего выписывается JIT-конфиг и уходит в пул задачей
   `python` с исходником [`agent.py`](pool_runners/agent.py) в payload.
4. Воркер пула выполняет его: качает `actions/runner` (архив кэшируется на
   воркере), распаковывает во временную папку и запускает `bin/Runner.Listener`
   с `ACTIONS_RUNNER_INPUT_JITCONFIG` и чистым окружением. Не `run.sh`: тот
   заворачивает любую поломку в нулевой код возврата, и упавший раннер выглядел
   бы как отработавший.
5. Раннер регистрируется, берёт ровно одну job, отрабатывает и выходит. Задача
   пула завершается, слот освобождается.
6. Контроллер каждые десять секунд сверяет свои задачи с пулом: терминальные
   выкидывает, зависшие без воркера снимает, лишних — только тех, что ещё не
   уехали на воркер, — отменяет. Задачу, которая уже держит раннера, он не
   трогает: раннер эфемерный и уйдёт сам.

Раннер шлёт в поток события пула, так что за ним видно с обычного `pool events`:

```
::pool::{"kind": "runner", "state": "listening"}
::pool::{"kind": "job", "state": "running", "name": "build"}
::pool::{"kind": "job", "state": "finished", "result": "Succeeded"}
::pool::{"kind": "runner", "state": "gone", "jobs": 1, "seconds": 94.2}
```

Когда контроллер останавливают, он закрывает сессию, ждёт `drain` секунд, пока
доработают job'ы, и снимает раннеров, которые ещё не уехали. Если job'ы всё ещё
идут, scale set остаётся на месте — раннеры доработают и умрут сами. Второй
`Ctrl+C` не ждёт и рвёт всё.

Перезапуск — не остановка: после сбоя контроллер поднимается, находит свой
scale set и подбирает из пула ранее отправленных раннеров, а не заводит вторую
партию поверх живой.

## Безопасность

Раннер выполняет чужой CI прямо в джобе твоего аккаунта — это не песочница, а
разделяемая машина. Что с этим сделано и что нет:

- **Окружение воркера не наследуется.** Раннеру собирается чистый `env` из
  белого списка (`PATH`, `HOME`, `LANG`, ...) плюс JIT-конфиг. `POOL_TOKEN`,
  `POOL_SERVER`, `GITHUB_*` и `ACTIONS_*` внешней джобы туда не попадают.
- **Но uid тот же.** Job целевой репы может прочитать `/proc/<pid>/environ`
  воркера и вытащить его токен. Разделения пользователей тут нет: пускай в пул
  только те репы, которым доверяешь как самому пулу.
- **Публичные репы не отклоняются.** На публичной репе job из форка — это чужой
  код на твоих раннерах; контроллер это не проверяет, решение за тобой.
- **JIT-конфиг лежит в payload задачи.** Кто может читать пул клиентским
  токеном — прочитает и его, а Postgres хранит payload вечно. Конфиг одноразовый
  и живёт, пока жив scale set.
- **Раннер не обновляется сам** (`disableUpdate`), так что версию стоит
  обновлять — она берётся последняя на старте, либо пинится в конфиге.
- Логи раннера едут в пул, логи самих шагов — в GitHub, как обычно.

И про правила: GitHub Actions предназначен для воркфлоу той репы, где он
работает. Крутить чужой CI за счёт минут своего аккаунта — способ этот аккаунт
потерять. Здоровый сценарий — свои же репы.

## Ограничения

- Каждый раннер занимает слот пула целиком: двадцать воркеров — двадцать
  раннеров и ни одной обычной задачи.
- Воркер живёт внутри джобы GitHub, а её потолок — шесть часов. Раннер,
  начавший job перед концом джобы, умрёт вместе с ней; `lifetime` держит
  это в предсказуемых рамках.
- Воркеру нужен `libicu` — на `ubuntu-latest` он есть, в своём образе поставь.
- Перезапуск сервера пула помечает все живые задачи `lost`, и раннеры вместе с
  ними умирают: их лиз не переживает рестарт.
- Только Linux x64 и arm64: другого `actions/runner` в релизах нет.

## Разработка

```bash
uv sync
uv run pytest
```

Тесты гоняют всю цепочку на подделках: фальшивый scale set, фальшивый пул,
который честно `exec`-ает исходник агента, и фальшивый `run.sh`, который
печатает те же строки, что настоящий раннер.

`agent.py` уезжает на воркер исходником, поэтому он самодостаточный: только
стандартная библиотека, никаких импортов из пакета и синтаксис, который поймёт
Python 3.11.

## Nix

```nix
{
  inputs.pool-runners.url = "github:wprhvso/pool-runners";

  imports = [ inputs.pool-runners.nixosModules.default ];

  services.pool-runners = {
    enable = true;
    configFile = "/run/secrets/runners.toml";
  };
}
```

Конфиг заезжает креденшлом systemd, так что `configFile` спокойно лежит под
`0400 root:root`. Сервис крутится под `DynamicUser`.
